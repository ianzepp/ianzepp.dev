The same platform, three times.

Monk API is the third clean-room implementation of a multi-tenant, model-first platform — the same architectural vision rebuilt from memory after Minted.IO (2015) and Motivis (2017–2020). No code was carried forward. What survived is the design: describe your schema, query your data, and let the observer rings handle everything in between.

The lineage

One vision, four implementations, a decade.

The core idea has never changed: a platform where the schema is data, not code. You describe your models and fields through an API. The platform generates CRUD, querying, access control, audit trails, and lifecycle hooks automatically. Tenants are isolated at the database level. The observer ring pipeline processes every mutation through a fixed sequence of validation, security, business logic, persistence, and notification stages.

This idea was first built as Minted.IO in 2015 (Salesforce-native), rebuilt as the Motivis platform in 2017 (TypeScript/Node.js/PostgreSQL), rebuilt again as Monk API in 2025 (TypeScript/Hono/Bun), and now runs hardcoded in Rust in the Minted Geek Swarm platform. No code was ever carried between iterations. The architecture persisted because one person carried it in their head.

2015 Minted.IO Salesforce-native. Solo founder. Acquired by Motivis 2017.
2017–2020 Motivis TS / Node / PostgreSQL. 10–20 engineers. VP Platform R&D.
2025–2026 Monk API TS / Hono / Bun. Clean-room rebuild from memory. Solo.
2026–now Swarm Rust. Rings hardcoded. Same pipeline, fourth language.
What survived

The Observer Ring pipeline — formalized on day 5 of Monk API — is the only subsystem that survived every subsequent rewrite unchanged in concept. The ORM was ripped out on day 3. The runtime migrated from Node to Bun. Auth was rewritten three times in 48 hours. But the rings never changed, because they were already right. They had been right since Minted.IO.

The describe / data pattern

The schema is data, not code.

Monk API has two primary route families. /api/describe lets you define and modify your data model at runtime — create objects, add fields, set types and constraints. /api/data lets you create, read, update, and delete records against those models. The describe layer is the schema; the data layer is the content. Both are APIs, both are versioned, both go through the same observer pipeline.

/api/describe/:modelCreate, read, update, or delete a model definition
/api/describe/:model/fieldsDefine fields on a model — inline with model creation or separately
/api/data/:modelCRUD against the described schema — create, find, update, delete
/api/data/:model/:id/:relNested child collections via relationship traversal
/api/bulkMultiple operations across multiple models in one transaction
/api/bulk/importImport a full SQLite database file with merge strategies
/api/aggregateAggregation queries — count, sum, avg, min, max
/api/trackedChange history for any record
/api/trashedSoft-delete recovery
/api/aclsRow-level access control
/api/fsVirtual filesystem
/api/cronScheduled job management

This is the pattern that makes the platform self-describing. A new tenant can define its entire data model, populate it with records, set up access control, and query it — all through the same HTTP API. No migrations, no deploy, no code changes. The schema is a conversation with the platform.

The find DSL

Thirty operators and recursive nesting.

The query system is a custom DSL with 30 filter operators, purpose-built for the describe/data pattern. Queries are JSON objects where keys are field names and values are operator expressions. Logical operators ($and, $or, $not, $nand, $nor) nest recursively to arbitrary depth, producing parameterized SQL with ACL-aware WHERE clauses automatically injected.

eqneneq gtgteltlte likenlikeilikenilike regexnregex innin anyallnanynallsize andornotnandnor between findtextsearch existsnull

The Postgres array operators (any, all, nany, nall, size) are distinctive — they enable set operations directly in the query DSL, which is also how the ACL system works: row-level permissions are stored as Postgres arrays and checked via array-overlap and containment operators baked into every query's WHERE clause. Permissions aren't a separate query; they're part of the same SQL.

What didn't make it from Motivis

The Motivis version supported nested queries that traversed relationships — querying parent records filtered by properties of their children. Monk API has the stub (_related field, commented-out $related processor) but the implementation was never completed. The logical nesting works; the relationship traversal does not. This is noted honestly, not hidden.

The observer rings

Ten rings, file-based, auto-discovered.

Every mutation in Monk API passes through a 10-ring observer pipeline. Each ring has a defined responsibility. Observers are TypeScript files dropped into src/observers/:model/:ring/:observer.ts and auto-discovered at boot — no registration code, no configuration. The ring number is the execution order.

0Data Preparation — normalize, coerce, set defaults 1Input Validation — accumulates all errors before throwing 2Security — ACL checks, permission enforcement 3Business Logic — domain rules, cross-field constraints 4Enrichment — computed fields, derived values 5Database — SQL execution, the only ring that touches persistence 6Post-Database — cache invalidation, materializations 7Audit — change tracking, history records 8Integration — webhooks, external system sync 9Notification — events, alerts, pub/sub
Passthrough mode

For high-throughput ingestion (sensor data, logs), Monk API supports a passthrough flag that skips rings 0–4 and 6–9, executing only ring 5 (Database). Validation, security, audit, and notification are all bypassed. This is a deliberate escape hatch for bulk ingest where the data is already trusted and the overhead of ten rings per record is prohibitive.

Ring 1 is architecturally distinctive: it's the only ring that accumulates errors rather than failing fast. A single validation pass collects every violation and reports them together, rather than stopping at the first one. Every other ring fails on first error. This asymmetry is intentional — validation is the one phase where the caller benefits from knowing everything that's wrong, not just the first thing.

The invisible transaction

The HTTP boundary is the transaction boundary.

Every mutating request in Monk API runs inside a database transaction that starts when the Hono handler receives the request and commits when the handler returns. If any observer in any ring throws — a validation failure in ring 1, a security rejection in ring 2, a database constraint in ring 5 — the transaction rolls back. No route handler ever calls BEGIN or COMMIT.

The mechanism is a withTransaction() wrapper in the routing layer. It pulls the tenant context from JWT middleware, opens the database adapter, starts a transaction, sets SET LOCAL search_path for tenant isolation, runs the handler (which runs the full observer pipeline), then commits or rolls back in a finally block. Cascading errors across multiple observer rings — including rings that trigger secondary mutations — are automatically captured because they share the same transaction scope.

Read-only variant

Streaming read operations use withSearchPath() instead — an intentionally-never-committed transaction whose only purpose is to scope SET LOCAL for tenant isolation without blocking writes. The transaction is implicitly rolled back on disconnect. The same pattern (transaction = HTTP request) applies to reads, but without the commit.

This design means that the entire observer pipeline — ten rings of validation, security, business logic, persistence, audit, and notification — is atomic by default. If ring 7 (Audit) fails after ring 5 (Database) has written, the write is rolled back. No partial state. No cleanup logic. The HTTP boundary is the consistency boundary.

Bulk operations

Multiple models, one transaction.

The /api/bulk endpoint accepts an array of operations — create, update, delete, upsert — where each operation can target a different model. The entire array runs inside a single transaction. If any operation fails, every preceding operation in the batch is rolled back.

This isn't just convenience. In a model-first platform where tenants define their own schemas, cross-model consistency often can't be enforced by foreign keys alone. The bulk endpoint lets a client say: "create this Account, create these three Contacts that belong to it, and update this Opportunity — atomically." If the Opportunity update fails validation, the Account and Contacts don't exist.

A separate import endpoint (/api/bulk/import) takes a different approach entirely: it accepts a full SQLite database file and ingests it with configurable merge strategies (upsert, replace, merge, skip) and optional model filtering. This is tenant-snapshot import — move an entire dataset between environments in one call.

Timeline

Eight months in four arcs.

Aug 19 – 30, 2025 331 commits

Genesis: full PaaS in twelve days

Day one: CLI and API stood up in the same session. Full CRUD by end of day. Day two: Drizzle ORM added. Day three: Drizzle ripped out for raw PostgreSQL — the ORM was already in the way. Day five: the Observer Ring pipeline formalized (Epic #45), the one architectural decision that would outlast everything else.

By August 30, Monk API was at v2.0.0-rc2 with JWT auth, schema-per-tenant isolation, the describe/data pattern, and the find DSL. Twelve days from first commit to release candidate.

Speed from prior knowledge

331 commits in 12 days isn't just fast iteration. This is the third time the platform was built. The architecture was already proven — the speed comes from not needing to discover the design. The ORM removal on day 3 is the tell: the builder already knew raw SQL was the right call, tried the ORM anyway, confirmed it was wrong, and moved on in 24 hours.

Sep 1 – 10 64 commits · then silence

RC hardening, then a two-month pause

The release candidate was polished: ACL API, error-handling centralization, v2.0.0 through rc4. Then the project went quiet from September 10 to November 9. Other work took priority — the pause wasn't abandonment, it was deprioritization.

Nov 9 – 29, 2025 624 commits · v2.1 → v6.2

The November burst

624 commits in three weeks, peaking at 62 commits in a single day (November 27). The version jumped from 2.1.0 to 6.2.0. This is where the platform matured.

Runtime migration (Nov 26–27): Node.js removed entirely. Vitest replaced with Bun's test runner. The project went from a Node/Express-adjacent setup to pure Bun in 48 hours.

MCP server (Nov 22): A Model Context Protocol server was added for Claude Code integration, initially as 11 tools, then refactored to 4 with TOON format. Later extracted to its own package.

Agent/TTY subsystem (Nov 28–29): 79 commits built an in-process terminal shell with STM/LTM memory, jq parser, xargs, base64, bc — essentially a self-hosted agent interface inside the platform. This entire subsystem would later be explicitly removed.

Apr 9 – 14, 2026 110 commits · 5 days

The closing arc: audit, cut, rewrite, pivot

After months of dormancy, a five-day burst closed the project's active development. An independent codebase analysis (Apr 9) triggered a correctness-swarm hardening pass: SQL injection, race conditions, encryption fail-closed.

The agent/TTY subsystem built in November was explicitly removed — a deliberate build-then-cut visible in one repository. The auth system was rewritten three times in 36 hours: local JWT, Auth0 brokered login, public-key machine auth — three complete architectures tried and either kept or discarded in rapid succession.

The final commits pivoted the project's homepage to "agent-first" and "LLM handoff" positioning. The marketing caught up to the architecture in real time.

Build then cut

The agent/TTY subsystem — 79 commits of work — was built in November and removed in April. This is the same pruning discipline visible in the Radix compiler retrospective: when something isn't earning its complexity, cut it. The willingness to delete working code is a process signal, not a waste signal.

Patterns

What the third iteration reveals.

The ring that never changed

The Observer Ring survived four implementations across a decade and two languages. Everything around it — ORM, runtime, auth — was rewritten repeatedly. The rings were already right.

Faster each time

Minted.IO took six months solo. Motivis took years with a team. Monk API reached release candidate in twelve days. Each iteration was faster because less design discovery was needed.

Transaction as HTTP boundary

No explicit transaction management anywhere in the codebase. The HTTP request is the transaction. Ten rings of observers, atomic by default. This is invisible infrastructure done right.

Build then cut

The agent/TTY subsystem was built (79 commits), used, evaluated, and removed. The auth system was rewritten three times in 36 hours. Fast iteration includes fast deletion.

Schema as conversation

Describe, then data. The platform doesn't need code changes to support new data models. A tenant defines its schema through the same API it uses to query it.

ACLs in the WHERE clause

Row-level permissions use Postgres array operators baked into every query. Permissions aren't a separate check — they're part of the SQL. No query ever returns data the caller can't see.

Monk API is not the interesting project. The lineage is. What makes this a case study isn't a single codebase — it's watching the same architectural vision survive a decade, four implementations, two languages, a startup acquisition, a VP tenure, a company shutdown, and a clean-room rebuild. The Observer Ring pipeline, the describe/data pattern, the transaction-as-HTTP-boundary, the schema-as-conversation philosophy — none of these were invented for Monk API. They were carried forward in one engineer's head and rebuilt each time the context changed.

The third iteration is the fastest because it has the least to discover. The rings don't change because they were already right. And the code that gets deleted — the ORM on day 3, the agent subsystem in April, the auth system three times in 36 hours — gets deleted fast because the builder knows what right looks like and isn't afraid to cut what isn't it.

The design survived because one person carried it. The code is new every time.
